## The e-commerce and subscription system: layout and function

Everything lives in `integrations/`. Each folder is a separate WordPress plugin (AGPL-3.0-or-later) for the store site, not part of the Next.js app; the app only receives their events. There is a plugin per job, so a store installs only what it needs.

```
store site (WordPress)                                    RapScalYon app (Next.js + Supabase)
  FluentCart (free, 1.7.0)  or  WooCommerce + WPSubscription
    |-- fluentcart-bridge / wpsubscription-bridge  --signed JSON-->  /api/billing-webhook --> core billing ledger
    |-- affiliatewp-fluentcart  --> AffiliateWP referrals (pending, unpaid, rejected, renewals)
    |-- fluentcart-schedule  (when a product can be bought)
    |-- fluentcart-offers  <--POST /rapscalyon/v1/offers-- offer synchronizer (Facebook posts read by ScrapeCreators)
    |        '-- GET /rapscalyon/v1/offers/active --> offers-widget (any website)
    '-- fluentauth/apply-settings.php.txt  (login hardening, run once)
```

| Folder | Function | Hooks and endpoints | Status |
|---|---|---|---|
| `fluentcart-bridge/` | Sends FluentCart subscription events to the core billing webhook. Needed because the free plugin has hooks and no sender. | Listens on `fluent_cart/payments/subscription_*` (active, trialing, canceled, expired, failing), `fluent_cart/subscription_past_due`, `fluent_cart/subscriptions/system_charge_failed`, `fluent_cart/subscription_renewed`. Posts flat JSON signed with HMAC-SHA256 (`x-webhook-signature`); retries up to 4 times. Needs `RAPSCALYON_WEBHOOK_URL` and `RAPSCALYON_WEBHOOK_SECRET` in `wp-config.php`. | Payloads verified against real FluentCart hooks in a sandbox 2026-10-07. No live gateway run. |
| `wpsubscription-bridge/` | Same job for WPSubscription on WooCommerce; replaces Bit Integrations. | `subscrpt_subscription_*` hooks, `subscrpt_subscription_payment_completed` (renewal unless it is the parent order's payment), `woocommerce_order_fully_refunded` (refund). Same constants and signing. | Unit-tested (16 checks). Not run on a live store. |
| `affiliatewp-fluentcart/` | Registers a `fluentcart` integration in AffiliateWP so referrals follow FluentCart orders. | `fluent_cart/checkout/prepare_other_data` (pending), `order_paid_done` (unpaid), `order_fully_refunded` and `order_status_changed_to_canceled` (rejected), `subscription_renewed` (renewal commission). Files: `affiliatewp-fluentcart.php` (registration through `affwp_extended_integrations`), `class-integration.php`. | Orders tested on cash-on-delivery; renewals tested with a stub only. |
| `fluentcart-schedule/` | Makes a product buyable only on chosen weekdays, hours and dates in the store's timezone. **Event flow into core.** A bridge posts `{subscription_id, customer_id?, status, email, product_name?, plan_key?, event_id, occurred_at}`. Core maps `active|trialing|renewed` to activated or renewed, `on-hold|failed|past_due` to payment failed, `cancelled|canceled|pending-cancel` to canceled, plus `expired` and `refunded`. The event id (`fc:<sub>:<status>:<time>`, `wps:...` for WPSubscription) makes a retry a duplicate and a second cancel a new event. The email identifies the customer; the FluentCart bridge skips an event with no email or subscription id.

**Choosing the stack per client** is in `docs/COMMERCE-STACKS.md`: FluentCart is the default, WooCommerce with WPSubscription the exception (an existing Woo store, or the owner's JobsGlider and PostGlider sites), FluentCart with FluentAffiliate when affiliates are simple.

## Pack registry, versions and what happens on a pull request

The repo is the single source of truth. Everything else is generated from `packs/<name>/` (`pack.toml`, `docs/MARKETING.md`) and checked.

| Artifact | Made by | Used by |
|---|---|---|
| `registry/packs.json`: per pack `version`, `tier`, `license`, `requires`, `requires_core`, `contentHash`, plus `catalogVersion` and the core version | `rapscalyon.py catalog` | CI, the app, humans |
| `app/lib/packs/catalog.generated.ts` (same data, with the marketing sections, and `catalogVersion`) | `rapscalyon.py catalog` | `/api/interview` |
| `pickaxe/kb/platform/*.md`, `docs/CATALOG.md` | `rapscalyon.py catalog` | knowledge documents |
| `pickaxe/kb/docs.json`: each managed Pickaxe document with its id, agents, and the hash of the text last published | `kb_sync.py adopt` and `publish` | `kb_sync.py check` |

**Versions.** `contentHash` is a sha256 over every file in the pack. `catalogVersion` is a short hash of every pack's name, version and content hash, so it changes whenever anything in the catalog does. `rapscalyon.py registry-check <git ref>` fails when a pack's content changed and its `[pack].version` did not go up, when a version went down, or when a pack disappeared (a removal is the owner's decision). `/api/interview` returns `catalogVersion` and each pack's version from `get_context`, and `get_pack` (operation `get_pack`, argument `pack`) returns one pack's sections, requirements and tier from the catalog bundled in the deployment.

**Pull request gate** (`.github/workflows/packs.yml`, job `gate`, no secrets, no hosted database): regenerate the catalog and fail on any difference; `registry-check origin/main`; resolve the install order; type-check the app; start a throwaway local Supabase; `tools/ci_packs.py` installs core and every official pack in dependency order (the installer's security rules and static scan run on each), runs all tests, removes the packs in reverse order and requires an empty result. `.github/CODEOWNERS` names the owner for every path; it takes effect once branch protection requires code-owner review (repository setting, not yet set).

**After a merge.** Pushes to `main` run `docs-drift`: `kb_sync.py check` compares the text the repo would upload with the hash last published, and opens an issue if any document is stale. Nothing is published automatically. The owner then redeploys the app if the catalog changed (the interviewer reads the catalog live through the action) and runs `python3 tools/kb_sync.py publish`, which replaces each stale document in Pickaxe (create, connect, disconnect, delete), reads back the attachment and the text, and records the new id and hash in `pickaxe/kb/docs.json`. Commit that file.

**Reviewing a contributed pack.** Tier `official` needs an AGPL licence; no third-party source (BuilderKit rule); read `docs/SECURITY.md` of the pack; a new commercial name needs the hard-coded list in `app/lib/interview.ts` edited by hand (not yet generated).

**Verified 2026-10-07:** the whole gate ran green on GitHub (pull request 2): generated files current, version rule, install order, app types, a throwaway local Supabase, then 24 official packs installed in order, 29 of 29 test suites passed, all packs removed leaving nothing. Its first runs found two real defects, both fixed: a CI-only Supabase CLI version mismatch, and the `item-search` rollback, which could not drop its tables while functions on their row types existed (0.1.1). `kb_sync.py adopt` and `check` ran read-only against Pickaxe. **Not run:** `kb_sync.py publish` and the production redeploy of the app (both blocked pending the owner's explicit go in this session). `check` reports `rapscalyon-packs` stale: the live copy has an older header and banner format.

## Installing and removing packs

```bash
python3 tools/rapscalyon.py [--project <ref>] pack add|remove|validate|test --pack <name>
python3 tools/rapscalyon.py core ...        # core foundation
RAPSCALYON_PACKS_PATH=~/projects/rapscalyon-plus/packs   # for commercial packs
```

Hosted mode links with `supabase link` and runs `supabase db query --linked` through the Management API. The token is a personal access token in `~/.config/rapscalyon/surf-infra.token` (mode 600, `SUPABASE_ACCESS_TOKEN=sbp_...`), used per command and never printed. `pack validate` of the chat-with-* packs needs `ai-chat` installed first. A hosted project may already have an event trigger named `ensure_rls`; core drops it and installs its own.

Protected projects, never touched: PostGlider, TatPlat, JobsGlider production (`tools/protected-refs.txt`).

## Verifying the FluentCart bridge (repeatable)

1. `cd integrations/fluentcart-bridge && php test.php` runs the payload checks (event ids carry the time).
2. Throwaway WordPress in Docker: MariaDB and `wordpress:php8.3-apache` on a private network; install with `wordpress:cli`; activate FluentCart 1.7.0 (wordpress.org) and the bridge mounted read-only; define `RAPSCALYON_WEBHOOK_URL` and `RAPSCALYON_WEBHOOK_SECRET` in a mu-plugin pointing at a small receiver container.
3. Create a customer, order and subscription with FluentCart's own models. Drive status through `SubscriptionService::syncSubscriptionStates` and a renewal through `recordRenewalPayment` (the path a gateway webhook takes). Fixtures without product data make later email listeners throw; that is a fixture gap, not a bridge fault.
4. Remove the containers and the network afterwards. Leave the `supabase_*` containers alone.

Result 2026-10-07: payloads for `active`, `renewed`, `past_due`, `canceled` correct, with distinct time-stamped ids. A bug was found: gateway renewals fire `fluent_cart/subscription_renewed` (args `subscription`, `order`, `main_order`, `customer`), not `renewal_paid` or `system_charge_succeeded`; the bridge now listens on it.

## Renewal commission

On `fluent_cart/subscription_renewed` the adapter finds the first order's referral and, unless it is missing or rejected, adds an unpaid referral for the renewal to the same affiliate at the affiliate's rate. A repeat call adds nothing; a refund of the renewal order rejects that referral. Tested with a stub of AffiliateWP's referral API. Before offering it: run one referred subscription on the billing site with the real plugin. Every renewal pays; there is no cap.
