## The e-commerce and subscription system: layout and function

Everything lives in `integrations/`. Each folder is a separate WordPress plugin (AGPL-3.0-or-later) for the store site, not part of the Next.js app; the app only receives their events. There is a plugin per job, so a store installs only what it needs.

```
store site (WordPress)                                    RapScalYon app (Next.js + Supabase)
  FluentCart (free, 1.7.0)  or  WooCommerce + WPSubscription
    |-- fluentcart-bridge / wpsubscription-bridge  --signed JSON-->  /api/billing-webhook --> core billing ledger
    |-- affiliatewp-fluentcart  --> AffiliateWP referrals (pending, unpaid, rejected, renewals)
    |-- fluentcart-schedule  (when a product can be bought)
    |-- fluentcart-offers  <--POST /rapscalyon/v1/offers-- offer synchronizer (Facebook posts read by ScrapeCreators)
    |        '-- GET /rapscalyon/v1/offers/active --> offers-widget (any website)
    '-- fluentauth/apply-settings.php.txt  (login hardening, run once)
```

| Folder | Function | Hooks and endpoints | Status |
|---|---|---|---|

**Event flow into core.** A bridge posts `{subscription_id, customer_id?, status, email, product_name?, plan_key?, event_id, occurred_at}`. Core maps `active|trialing|renewed` to activated or renewed, `on-hold|failed|past_due` to payment failed, `cancelled|canceled|pending-cancel` to canceled, plus `expired` and `refunded`. The event id (`fc:<sub>:<status>:<time>`, `wps:...` for WPSubscription) makes a retry a duplicate and a second cancel a new event. The email identifies the customer; the FluentCart bridge skips an event with no email or subscription id.

**Choosing the stack per client** is in `docs/COMMERCE-STACKS.md`: FluentCart is the default, WooCommerce with WPSubscription the exception (an existing Woo store, or the owner's JobsGlider and PostGlider sites), FluentCart with FluentAffiliate when affiliates are simple.

## Installing and removing packs

```bash
python3 tools/rapscalyon.py [--project <ref>] pack add|remove|validate|test --pack <name>
python3 tools/rapscalyon.py core ...        # core foundation
RAPSCALYON_PACKS_PATH=~/projects/rapscalyon-plus/packs   # for commercial packs
```

Hosted mode links with `supabase link` and runs `supabase db query --linked` through the Management API. The token is a personal access token in `~/.config/rapscalyon/surf-infra.token` (mode 600, `SUPABASE_ACCESS_TOKEN=sbp_...`), used per command and never printed. `pack validate` of the chat-with-* packs needs `ai-chat` installed first. A hosted project may already have an event trigger named `ensure_rls`; core drops it and installs its own.

Protected projects, never touched: PostGlider, TatPlat, JobsGlider production (`tools/protected-refs.txt`).

## Verifying the FluentCart bridge (repeatable)

1. `cd integrations/fluentcart-bridge && php test.php` runs the payload checks (event ids carry the time).
2. Throwaway WordPress in Docker: MariaDB and `wordpress:php8.3-apache` on a private network; install with `wordpress:cli`; activate FluentCart 1.7.0 (wordpress.org) and the bridge mounted read-only; define `RAPSCALYON_WEBHOOK_URL` and `RAPSCALYON_WEBHOOK_SECRET` in a mu-plugin pointing at a small receiver container.
3. Create a customer, order and subscription with FluentCart's own models. Drive status through `SubscriptionService::syncSubscriptionStates` and a renewal through `recordRenewalPayment` (the path a gateway webhook takes). Fixtures without product data make later email listeners throw; that is a fixture gap, not a bridge fault.
4. Remove the containers and the network afterwards. Leave the `supabase_*` containers alone.

Result 2026-10-07: payloads for `active`, `renewed`, `past_due`, `canceled` correct, with distinct time-stamped ids. A bug was found: gateway renewals fire `fluent_cart/subscription_renewed` (args `subscription`, `order`, `main_order`, `customer`), not `renewal_paid` or `system_charge_succeeded`; the bridge now listens on it.

## Renewal commission

On `fluent_cart/subscription_renewed` the adapter finds the first order's referral and, unless it is missing or rejected, adds an unpaid referral for the renewal to the same affiliate at the affiliate's rate. A repeat call adds nothing; a refund of the renewal order rejects that referral. Tested with a stub of AffiliateWP's referral API. Before offering it: run one referred subscription on the billing site with the real plugin. Every renewal pays; there is no cap.
